# Stormworks `.mesh` 二进制格式规格

> 本规格由本机 **3653 个有效 mesh 全量实测**确立，非照抄社区文档。
> 验证方式：解析游标走完文件后必须精确等于文件大小（`bytes_consumed == file_size`）。
> **3653/3653 精确闭合，失败 0。**
>
> 确立日期：2026-09-03　验证工具：`scripts/sw_mesh.py verify`
> 游戏根目录：`E:\SteamLibrary\steamapps\common\Stormworks`（**只读红线**）

## 2. 二进制结构（小端）

```
偏移   类型          字段              说明
─────────────────────────────────────────────────────────────────────
0      char[4]       magic             "mesh"          3653/3653 命中
4      u16           h0                恒 7（每顶点 7 个 float = 28 B）
6      u16           h1                恒 1
8      u16           vertexCount       顶点数（上限 65535）
10     u16           h3                恒 19 (0x13) 格式标记
12     u16           h4                恒 0
                                       ── 头部共 14 字节 ──
14     Vertex[n]     顶点数组          28 B/顶点，见 §3
       u32           indexCount        索引数（= 三角数 × 3）
       u16[n]        索引数组           三角索引，max < vertexCount
       u16           subMeshCount      submesh 数量
       SubMesh[n]    submesh 数组      见 §4
       u16           尾哨兵             恒 0，3653/3653
```

### 头部恒定字段（版本漂移探测用）

`(h0, h1, h3, h4) == (7, 1, 19, 0)`，**3653/3653 恒定**。
任一文件偏离此值 → 游戏版本可能改了格式，必须重新验证。

## 3. 顶点结构（28 字节，无 UV）

```
偏移   类型        字段
0      f32[3]      position   x, y, z      单位：米
12     u8[4]       color      R, G, B, A
16     f32[3]      normal     nx, ny, nz   单位向量
```

**关键特性**

- **没有 UV 坐标。** 这是设计如此，不是解析错误 —— Stormworks 靠顶点色 +
  shaderId + 程序化材质渲染，不使用贴图坐标。
- **法线全是单位向量**：`|normal| = 1`，3653/3653 通过（容差 1e-3）。
- **`alpha` 不恒为 255**：221/3653 个文件含 alpha≠255 的顶点（部件内 85/940）。
  ⚠ 这是曾被社区文档误导的坑，不可当作常量断言。
- 顶点数上限 65535（索引为 u16）。

### 顶点色约定

| 用途 | RGB | 说明 |
| --- | --- | --- |
| 可涂色基色 | **(255, 125, 0)** `#ff7d00` | 主基色，玩家涂装生效区 |
| 可涂色变体 | (155, 125, 0) | 第二档 |
| 可涂色变体 | (55, 135, 0) | 第三档 |

`paint_verts` 字段统计命中上述基色的顶点数，是**判断部件是否可涂装**的直接依据：

- `paint_verts == 0` → 全固定配色（如 Electric Battery Small，256 顶点全部固定色）
- `paint_verts == vertex_count` → 整件随涂装变色（如 Fluid Tank Small，120/120）

## 4. SubMesh 结构

```
偏移   类型        字段                 说明
0      u32         indexBufferStart     索引起始
4      u32         indexBufferLength    索引长度
8      u16         z1                   恒 0
10     u16         shaderId             见下表
12     f32[6]      bounds               min.xyz, max.xyz（AABB）
36     u16         z2                   恒 0
38     u16         nameByteLength       名称字节长度
40     char[]      name                 UTF-8，**无终止符**
       f32[3]      scale                恒 (1.0, 1.0, 1.0)
```

固定部分 = 52 字节 + `nameByteLength` + 12 字节。

### shaderId 语义（全量分布）

| ID | 名称 | 文件数 |
| --- | --- | --- |
| 0 | Opaque | 3579 |
| 1 | Transparent | 200 |
| 2 | Emissive | 106 |
| 3 | Lava | 20 |

材质另受名称约定影响：`MATERIALglass`、`MATERIALadditive`。

### subMeshCount 分布

`1` → 3404 个文件；`2` → 246 个；`3` → 3 个。

### submesh 名称

479 种不同名称，其中 **1923 个为空串**。非空名称形如 `ID2` / `ID29` / `ID142`，
与源 `.dae` 里的 `<geometry id="...">` 对应。

## 5. ⚠ 三处社区文档的错误（本机实测修正）

社区现有资料（CodeLeopard 的 C# 实现等）是本格式的发现起点，但**有三处与本机实测不符**。
教训：**社区文档一律先经「全量指针闭合」复核再采信，不得直接照抄。**

| # | 社区文档说法 | 本机实测 | 后果 |
| --- | --- | --- | --- |
| 1 | 头部 6 个 u16（16 字节） | **5 个 u16，14 字节** | 按 16 字节读 → 3653 个文件**全部错位**；按 14 字节读 → 全部闭合 |
| 2 | `sdk/meshes` 与 `rom/meshes` 仅部分同名 | **`rom/meshes` 顶层 1777 个 stem 100% 有同名源** | 低估了交叉验证的可用样本量 |
| 3 | alpha 恒为 255 | **221/3653 个文件存在 alpha≠255** | 若当常量断言会误报大量文件异常 |

| 断言 | 结果 |

## 8. AABB 可信度：两种语义必须区分

`bounds` 字段**在不同类别的 mesh 上语义不同**，混用会得出错误尺寸。

| 类别 | bounds 语义 | 数量 | 判定 |
| --- | --- | --- | --- |
| 部件件 `component_*.mesh` | 真实几何 AABB | 940 | submesh bounds 并集 == 顶点实测 AABB，**940/940 通过** |
| 地形件（`moon_surface_*`、`arid_island_*`、`mainland_*` 等） | **瓦片声明框**，非真实几何 | 1596 | 例：`arid_island_10_10.mesh` 声明 ±500/±1000，实测 y∈[-354.63, 183.12] |

索引中每条记录打 `bounds_kind` 标签：

- `"exact"` —— 声明与实测一致，数据可用（全局 2057/3653）
- `"tile_declared"` —— 声明框，不可当作尺寸使用

**第 21 册《部件几何档案》只采信 `exact`。**

## 9. 单位与坐标系

- **1 格 = 0.25 m**（部件网格单位换算）
- **Y 轴向上**
- 顶点坐标单位为米，部件尺寸通常落在 0.25 m ~ 数米区间

示例（气压计 `component_barometer.mesh`）：

```
实测 AABB  : (-0.125, 0.105, -0.125) ~ (0.125, 0.184, 0.125)
实测尺寸   : 0.250 × 0.079 × 0.250 m  =  1.000 × 0.316 × 1.000 格
```

> **与现有知识册的关系**：`00_速查_部件总表.md` 的尺寸来自 XML `<surface>` 推算的
> **占位格数**（「占 1x1x1」）；本规格提供**二进制实测的真实渲染几何**。
> 两者是「逻辑占位」与「物理外观」两个维度，可交叉纠错。
> 例：Push Button 声明占 1x1x1，实测厚度仅 0.020 m（0.08 格）——几乎贴面。

## 10. 部件 ↔ mesh 映射

- 引用来源 **100% 来自 `.xml`**（2139 处匹配；`.lua`/`.bin`/`.txt` 中 0 处）。
- 定义文件 `rom/data/definitions/*.xml`，759 个明文，其中 **716 条 `mesh_data_name` 非空**。
- 属性名：`mesh_data_name`（主网格）、`mesh_0_name` / `mesh_1_name` / `mesh_editor_only_name`（附加网格）。
- **文件名 ≠ 部件名**，不可反推。存在多对一与一对多：
  - 多对一：`component_inventory_small.mesh` 被 26 个定义共用，`_medium` 13 个，`_large` 10 个
  - 总计 **595 个 mesh 服务 716 条定义**
- ⚠ 定义 XML **不是合法 XML**（部分属性名以数字开头，如 `00="1"`），
  标准 ElementTree 会整文件拒绝 —— 需用 lxml(recover=True) 或正则预处理。

## 11. SDK 交叉验证的定位（重要）

`sdk/meshes/` 下 2109 个源模型（1762 `.dae` + 347 `.fbx`），是**独立于 .mesh 解析链路的第二信源**。
但两个对账指标的可信度**完全不同**，实测校准如下：

| 指标 | 一致率 | 结论 |
| --- | --- | --- |
| **三角数** | ~84% | **可作佐证**。解析若出错该值应随机分布，不可能 84% 精确相等 |
| **顶点数** | ~48% | **不可作断言**。编译期必然做顶点合并（weld）：源 .dae 保留未合并的 split vertices，.mesh 是合并结果，两者本就不该相等 |

- 三角数不一致的部分源于**源资产与编译产物版本不同步**（游戏侧数据问题），
  例：`component_rod_storage` 的 mesh 三角数 452 恰为 dae 226 的 2 倍。
- 已确认不一致案例中 `.dae` **不存在 polylist/polygons**，只有 `triangles`，排除统计遗漏。
- 源资产与产物的**顶点坐标数值也不同**（编译期居中 + 缩放），只比对拓扑量。

> **结论：真正的验证强度来自 3653/3653 指针闭合，SDK 对账是参考性佐证，不是严格断言。**

## 13. 工程纪律

1. **只读红线**：游戏目录只读。解析器全程 `open(path,'rb')`，代码内不含任何写模式。
2. **输出护栏**：导出路径必须落在 `D:\STORMWORKS` 下，否则 `guard_output_path()` 直接拒绝。
3. **不复制社区代码**：只参照格式事实自行实现（规避 LGPL-3.0）。
4. **排除备份**：统一走 `iter_game_meshes()`。
5. **格式漂移**：任何一条指针不闭合即视为漂移，`verify` 退出码 `2`。
