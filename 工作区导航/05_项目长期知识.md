## 5. 关键实测结论（写代码前必看）

### 5.1 物理传感器与雷达

- 🔴 **物理传感器复合输出 ch4-6（欧拉角 X/Y/Z）单位是「弧度 rad」，值域 -π~+π，不是圈**。
  直接喂 `math.sin/cos`，**不要 ×2π**。雷达方位/仰角等其他角度仍以「圈」为单位，须 ×2π。
- **两套坐标系（最高频 bug 源）**：
  GPS 系（右手）X=东、Y=北、Z=高度；物理传感器系（左手）X=东、Y=铅直上、Z=北。
  换算 `GPS_X=PS_1, GPS_Y=PS_3, GPS_Z=PS_2`（**Y 与 Z 互换**）；欧拉角为 **Z-Y-X 序**。
  物理传感器**不接电就没有坐标输出**。
- **Stormworks 角度约定与教科书相反**：以 Y 轴为基线、顺时针为正。
  2D `(x,y)=(r·sinθ, r·cosθ)`；3D `(x,y,z)=(r·cos仰·sin方, r·cos仰·cos方, r·sin仰)`。
- **雷达新旧差异**：新 = 统一 8 目标 + **Gimbal Input 复合输入**（无延迟、无需枢轴）、俯仰 ±0.125；
  旧 = 除「雷达(巨)」外只能 1 目标、靠 FOV + Facing Yaw。
  ⚠ **通道顺序不同**：旧 = 距离·信号强度·仰角·方位角；**新 = 距离·方位角·仰角·时间(tick)，且无信号强度**。
  旧雷达（5000/20000/50000 m）已从部件栏移除，但旧存档仍可调出。
- **雷达误差**：距离 ±1%、角度 ±0.001 圈。滤波用 **ABF(α-β)** 而非 LPF
  （实测 ABF 0.97 m vs LPF 24.88 m，差 25 倍；**β ≈ α/10**，β=α 时速度估计会崩）。
  滤波加在**算完的坐标**上，不要加在雷达原始数据上。
- **声纳**：新 60/100/200 **km**（出自游戏内 s_desc，非 wiki 笔误；但远超地图尺度，有效距离需实测；
  **旧版声纳只有 3000 m**，新旧别混淆）。16 目标 × 2 值且**只有角度无距离**；有 Ping 节点
  （被动/主动互斥）；**仅声纳(小)有 Torpedo Output**。
- **功耗实测**（Swatt/tick）：雷达 0.1（Huge 0.2）、距离/激光距离传感器 0.01、其余传感器 0.0001。
- **待验证**：新雷达具体射程未知（游戏内只有 long/short 定性描述）。
- 日文 wiki 的目标解算代码漏了圈→弧度转换（真 bug），`17_传感器与雷达.md` §2.6 是修正版，
  已离线验证：正交性误差 4.4e-16、det=+1、保长性 0/300 超差。

### 5.2 弹道计算

**三常数（错一个全盘皆错）**：弹丸重力 **30 m/s²**（V1.3.6 起，← 不是载具的 10 m/s²）、
**60 tick/s**、阻力**逐 tick** `v ← v×(1-k)`（**不适用于弹头**）。

**两个必知陷阱**：
1. **射程随仰角非单调** —— 超过最优角后仰角越大射程越短。插值表必须截断在低伸分支，
   否则会取到高抛那一支，解算全错。
2. **降表不能用 ½gt²** —— 阻力同样衰减垂直分量，实际下坠约为该式一半
   （转管自动火炮 1500 m：自由落体 238 m vs 实际 124 m）。

**模型可信度**：与 wiki 标称射程对比 6/7 武器吻合在 1.02~1.17×；
**机枪是唯一离群点**（模型 1198 m vs 标称 500 m，2.4×）—— wiki 的 500 m 疑为散布意义上的有效射程。

**Fuse Timer（引信定时器）** 是空爆核心：只有重型自动火炮/坦克主炮/大型榴弹炮/贝莎巨炮有，
且只对高爆与破片生效。

### 5.3 模块化引擎（18 轮实测）

- **熄火判据 `RPS < 3`**：起动器全程开启，低转速由起动器维持，发动机不自持。有效工作区 = RPS ≥ 3。
- **空转（带一个 3x3 轮、无制动）启动曲线是每轮必采基线**；斜坡推荐 0.001/s、空转 ≥60 s，跨轮必须统一。
- 🔴 **「空转」有两个口径，别混用**：真空载（离合器 0）vs 带自由轮（离合器 1），1x1 差 −22.2%。
  **空载转速与排量基本无关**（1x1 60.66 / 3x3 61.64 / 5x5 64.98，跨 125 倍排量只差 7%）；
  排量带来的是**带载不掉速的能力**，不是更高转速。
- **每冲程油量（最可靠指标）**：1x1 0.00145、3x3 0.0378、5x5 0.22（两种加载方式差异 0.7%~2.4%）。
  1x1→3x3 严格按排量缩放；3x3→5x5 单位排量油耗偏高 22%。
  ⚠ **多缸必须按缸数归一化**：每缸每冲程油量 = 流量 ÷ (RPS × N/2)。
- **扭矩计**：测的是**所连接的整个动力网络**的扭矩与 RPS（安装位置不影响读数），
  读数 = 网络上所有连接件动力需求之总和。**测引擎输出扭矩须装在引擎侧网络**。
  单位存疑（日文 wiki 称推测为转动惯量，Fandom 称 force）→ **别当 N·m 用**，只作相对比较。
  实测两个坑：锁死负载引入**与接合压无关的常数项 ≈20.0**；扭矩计还输出一路 RPS（建议记第 6 通道）。
- 🔑 **滑差**：扭矩计 RPS vs 曲轴 RPS 的差随负载单调增大（空载 1.4% → 满接合 82%），
  打滑主要发生在接合压恒为 1 的模块化发动机离合器上 → **负载瓶颈是离合器打滑，不是引擎扭矩**。
- **扭矩序列（同 1x1 飞轮）**：1x1 = 0.70 RPS/s（1×）→ 3x3 = 17.45（24.8×）→ 5x5 = 76.00（108×）。
  小排量段（1x1→3x3）扭矩 ×25 低于排量 ×27；大排量段（3x3→5x5）扭矩 ×4.4 ≈ 排量 ×4.63。
  **实车选型：要扭矩优先加大单缸排量；缸数翻倍只 ×1.7–2 且油耗翻倍。**
- **飞轮是"扭矩差异放大器"**：不带飞轮时单缸与双缸达稳态都约 1.9 s（看不出差别）；
  带同一飞轮后变 86 s vs 41 s（2.1×）。**比较引擎扭矩用「带飞轮加速测试」**，
  指标：达 60 RPS 时间 / 峰值加速率。飞轮只改动态、不改稳态；飞轮 RPS 与曲轴 RPS 逐点相同（零滑差）。
- **缸数规律**（同一飞轮）：加速时间 ∝ 1/缸数（时间×缸数 ≈ 85 常数）、峰值加速率 ∝ 缸数、
  峰值油耗 ∝ 缸数，而稳态 RPS 与缸数无关。
- **跨排量对比的干净做法**：用**曲轴变矩器**（旧文档称「转换曲轴」，如 3转1）把大引擎接到同一个 1x1 飞轮，
  使飞轮惯量一致，加速时间可直接互比。⚠ 5x5 无 5转1 直转件，需 5转3 + 3转1 两级。
  游戏定义 XML **无显式 rotational_inertia 字段**，转动惯量由几何派生，质量只是近似代理。
- **接口匹配**：离合器一律用与曲轴同尺寸的模块化发动机分类部件；气缸口同理（`cylinder_3` 只接 3x3 气缸）。
  3x3 气缸的定义文件叫 `modular_engine_piston_3x3.xml`（不是 cylinder_3x3）。
- **09 轮起的"扭矩计前置"标准接法**：
  `曲轴 → 模块化发动机离合器(同尺寸，恒 1 取力) → 扭矩计 → 通用离合器(=扫描变量) → 锁死轮`
- 🗂 **数据留档（血泪）**：用户会清理 `SW示波器v0.1.3\` 下的旧 CSV，
  **归档文档 §6 附录是 01–03 轮数据的唯一副本**；`eng_test.xml` 也只有一份。
  每轮结束先提醒另存 CSV 与载具副本。

### 5.4 载具 XML / 微控制器

- **`d` 属性 = 定义文件名（去 .xml）** → 游戏内英文名 → 汉化译名。对照表 `数据\xml_id_map.json`（759 条）。
- **camera_med（Camera Medium）支持 Pivot X/Y 云台控制**（Fandom wiki 漏写，游戏定义为唯一权威）：
  Pivot 复合输入上限 **±0.125 圈**，Value1=水平、Value2=垂直。
- **camera_med 的 Pivot 是无惯性逻辑轴**（给角度即瞬间指向）→ 摄像头走
  「雷达 az/el 残差 + 轻滤波 α=0.3 → Pivot」，**与座圈（物理电机、有真实滞后）解耦**；
  **不要**给无惯性轴套用 ABF 等重滤波（会引入 ~10 tick 滞后）。
- **SW示波器 CSV 列索引是 0 基**：`output.setNumber(N, val)` 对应 CSV **第 N-1 列**。
- 载具 XML 中 `<body>` = 一个物理子网格；**判断部件在哪个网格看它属于哪个 `<body>`**，
  ⚠ 不要用 `<c t="N">` 判断（`t` 语义未定，观测值仅 0–7）。
- 旋转 `<o r="...">` 为行优先 3×3 矩阵，语义 = 部件本地系(X右/Y前/Z上) → 载具体素系(X右/Y上/Z前)。
- 详细组件 type 语义表与 Lua 序列化禁忌见 `技能库\sw-vehicle-xml\SKILL.md`。

## 6. 工程陷阱清单（血泪汇总）

| # | 陷阱 | 规避 |
| --- | --- | --- |
| 1 | **MC Lua 里的半角 `<` 和双引号会直接破坏 XML**（游戏崩溃/解析失败） | 属性内脚本禁用双引号；比较一律写成 `>` 方向（`if a>10`、`if DEAD>math.abs(e)`），或用 `math.min/max`；**注释里也不得出现 `<`**，用「低于/大于/≤」替代 |
| 2 | **DataRecord 用 httpGet 上传，URL 超 ~4096 字符游戏崩溃** | 9 通道 %.6f × 30 tick ≈ 3910（临界）；12 通道 × 30 tick ≈ 5170（崩）。修复：批量 30→15 tick、精度 %.6f→%.4f。通用规则：**URL 长度控制在 4000 字符以内** |
| 3 | **Edit 工具报告成功后可能静默未生效** | 编辑后必须重新 grep 复核（尤其载具 XML） |
| 4 | **同一载具多个 Lua 块可有同名函数但语义不同**（如 `RADAR_TEST` 的 object 82 活代码 vs 96 死代码） | 清理/替换**按 object id 精确限定作用域**，切勿按函数名全局替换 |
| 5 | **枚举类属性按 Fandom 行文顺序推断** | 以游戏内 UI 下拉顺序为准。例：radar 模式 = 0 Static / 1 Clockwise / 2 Anticlockwise / 3 Sweep / 4 Manual |
| 6 | **游戏内改过部件属性后 XML 被重写** | 外部编辑前先确认磁盘文件是最新值 |
| 7 | 载具 XML 常 0.5 MB+ 单行 | 禁止 Read 全文，用 Python/grep 定点提取 |
| 8 | 坐标解算改动直接进游戏调 | 先用 Python 复刻 Lua 逻辑做**离线数值仿真**（多姿态往返误差=0）再交付 |
| 9 | 大批量术语查表命中率低 | wiki 名 ≠ 游戏内名（词序相反 / 括号位置不同），走 `sw_batch.py` → `sw_find.py` 三级流程 |
| 10 | PowerShell 工具不回显 stdout | 需要输出时先 `Set-Content` 写文件再读 |

## 7. 约定

### 7.1 术语口径（与汉化补丁的已知分歧）

本工作区沿用既有成稿的用词，以下几处**与汉化补丁字面不一致**，属于"疑似补丁错译 → 以游戏内实际功能为准"
（`术语对照指南.md` §5 规定的处理方式）。**写新文档时沿用左列，不要改成右列**：

| 本工作区用词 | 汉化补丁字面 | 说明 |
| --- | --- | --- |
| **复合信号 / 复合输入 / 复合输出** | 混合输入 / 混合输出 | Stormworks 的 composite 是「多通道打包成一路」的信号类型，全库与 `17_传感器与雷达.md` 统一称「复合」 |
| **枢轴 / Pivot** | 轴 | `Pivot` 作节点名时保留英文或写「枢轴」，与 `轴`（Axle）区分 |
| **物理传感器** | 多功能物理传感器 | 简称，非另起译名 |

另需注意**同一概念的两个层级**：

- 部件**分类名** = `模块化引擎`（`sw_defs.py` 分类 `cat[13] M 模块化引擎`）
- 具体**部件名** = `模块化发动机曲轴(1x1)` / `模块化发动机气缸` / `模块化发动机飞轮` / `模块化发动机起动器` /
  `模块化发动机气体歧管` / `模块化发动机燃油歧管` / `模块化发动机曲轴变矩器(3至1)`

已核对无误的常用译名：扭矩计（Torque Meter）、离合器（Clutch）、3x3轮（Wheel 3x3）、
雷达（Radar）、声纳（Sonar）、摄像头（Camera）、微控制器（Microcontroller）、
炮塔座圈（Turret Ring，简写「座圈」）、液阀（Liquid Relief Valve）、流量（Flow Rate）。

## 8. `.mesh` 二进制格式（2026-09-03 攻破，技能 `sw-mesh-tools`）

> 完整规格见 `技能库\sw-mesh-tools\reference\格式规格.md`；知识册为 `数据库\方块数据\21_部件几何档案.md`。

### 8.1 格式（3653 个有效文件全量实测，指针闭合 3653/3653）

```
小端
char[4] "mesh"
u16 7 / u16 1 / u16 vertexCount / u16 19 / u16 0        ← 头部共 14 字节
Vertex[n] 28B = f32[3]pos + u8[4]RGBA + f32[3]normal    （无 UV，设计如此）
u32 indexCount ; u16[indexCount]
u16 subMeshCount
  per: u32 start, u32 length, u16 0, u16 shaderId, f32[6] bounds,
       u16 0, u16 nameLen, char[name](UTF-8), f32[3](1,1,1)
u16 0                                                   尾哨兵
```

- **1 格 = 0.25 m**，Y 轴向上。shaderId：0 Opaque / 1 Transparent / 2 Emissive / 3 Lava。
- 可涂色基色 **RGB(255,125,0)** `#ff7d00`（变体 `(155,125,0)`、`(55,135,0)`）。
  `paint_verts == 0` → 不可涂装；`== verts` → 整件随涂装变色。
- 规模：有效 **3653 个 / 465.7 MB**；**必须排除 `back up/` 镜像 3613 个**（与 `rom/` 完全重复）；
  顶点 15,760,161、索引 23,383,194。
- 部件件（`component_*`）940 个 bounds 精确（`exact`）；地形件 1596 个是**瓦片声明框**
  （`tile_declared`），不可当尺寸用。

### 8.2 ⚠️ 社区文档三处错误（本机实测修正）

| 项 | 社区说法 | 实测 |
| --- | --- | --- |
| 头部长度 | 6 个 u16 / 16 B | **5 个 u16 / 14 B**（照抄会 3653 个全部错位） |
| SDK 源资产 | 与 `rom/meshes` 仅部分同名 | 顶层 1777 个 stem **100% 有同名源** |
| alpha 通道 | 恒为 255 | **221/3653 个文件含 alpha≠255** |

**纪律固化**：社区文档一律先经「全量指针闭合」复核再采信，不得直接照抄。
未解字段（`u16 7` / `u16 1` / `u16 19`、submesh 的 `start/length`、尾部 `f32[3](1,1,1)`）
一律标「恒定但语义未定」，**禁止杜撰**。

### 8.3 验证策略（三条独立证据）

1. **指针闭合 3653/3653** —— 自证式，最强。格式一旦漂移必然大面积不闭合，是第一探测器。
2. **占位格数比对 92.3% 吻合**（558 条可比对：吻合 515 / 超出 21 / 偏小 22）——
   占位来自定义 XML 的 `<voxel_min>` / `<voxel_max>`，与 `.mesh` 二进制**完全独立**，
   因此是真验证而非循环论证。
3. **SDK 源 `.dae` 三角数一致率 84%** —— 仅作佐证。
   ⚠ **顶点数一致率仅 48%，不可作断言**：编译期必然执行顶点合并（weld），
   源 `.dae` 保留未合并的 split vertices。已排除 polylist 漏统计（源中只有 triangles）。

### 8.4 数据解读陷阱（均已踩过）

- **可动部件烘焙了极限姿态**：气动活塞占位 1x2x1 → 实测 1×**5.10**×1（活塞杆伸出态）；
  炮塔座圈 9x1x9 → 9×2×9。实测 > 占位属正常，**不是解析错误**。
- **雷达占位 = 扫描范围（不是 bug）**：雷达(巨) `<voxel_min x="-18"/>` / `<voxel_max x="18"/>`
  → 占位 37×5×37 格，与 mesh 实测**完全一致**。一度误判为「含辅助几何」，已更正。
  可玩性：雷达会占掉大片空间，扫描范围与占位等价。
- **勿用启发式自动判定「辅助几何」**：试过「顶点全为基色」「归一化填充度」，均大量误报
  （机翼、龙骨、气罐等真实大尺寸/薄壳部件被误判）。判读依据是 vox 比对。
- **同名多行不是重复 bug**：`_fluid` / `_torque` / `_v2` 变体与基础版共用同一 mesh，
  用「定义 id」列区分。`(def, attr)` 组合全库无重复，解析侧无重复。
- **部件不使用 `.phys`**：碰撞体记在定义 XML 的 `physics_shape` / `<surface>`；
  `.phys` 仅地形/建筑/门使用（其格式已摸清，未实现）。

## 12. `screen.setMapColor*` 是全局持久状态（2026-09-04 澄清）

写在 `drawMap` **之后**的真实后果是**本次绘制沿用上一次设的值**——即**延迟一帧生效**，
并非「完全没效果」。因为通常每帧都设，所以从第 2 帧起颜色恒定正确，肉眼无差别，只有**第 1 帧**是默认色。

- 严格写法仍是「先 `setMapColor*` 再 `drawMap`」（`数据库\Lua\Lua示例\05_屏幕绘图与HUD.md` §17）。
- 真正会出问题的是把它放进 `onTick`——跨帧时序完全不受控。
- 已据此修正 `05` §17 的绝对化表述，并在 `Lua示例\README.md` 坑表补了一行。

- 索引口径与账本 `ids_learned` 不一致时，**以索引为准**并同步账本。

## §16 库存批次的流水线 + 三个参数陷阱（2026-09-05 第 12 轮固化）

### 16.1 库存也能走「批次隔离 → 差分 → 装箱 → 精读」

价值轨 `--top` 返回的 id 里，常见一大半**早已提取过 Lua**（存在 `_提取暂存` 根或 `_r6c/_r7c/_r8c/_r6/_r7/_new`
等子目录）只是没写成例题。对它们再跑一遍「下载 + 提取」是纯浪费。

新脚本 `_work/_mk_batch.py <批次目录名> <id,id,...>` 做的事：
扫主语料根 + 所有非 `_b*` 子目录 → 取文件名首段匹配 id 的 `.lua` → **剥头部两行后按 MD5 去重** →
复制进 `_提取暂存/_bN`。之后 `_bN` 就能照常跑 `census → diff_lua_batch → peek（装箱）→ dump`。

第 12 轮实证：两个微批共 48 个文件（去重后）→ 差分出 26 段全新 → 精读 4.3 万字符 → **写出 9 道例题**，
全程零下载，单轮产出创纪录。

用法：

```bash
"$PY" "<WS>/_work/_mk_batch.py" _b1 3792981388,3794688360,3795280695
"$PY" "<WS>/AI相关/_scripts/diff_lua_batch.py" --dir _b1
```

⚠ 收尾并入主语料时，`_bN` 里会残留 `_census.json` 等普查产物，直接 `os.rmdir` 会报
`ENOTEMPTY`（受管 Python 的 `_safe_rmdir` 会拦），要先清掉非 `.lua` 文件。

### 16.2 两个「逗号串静默失败」陷阱（已修复）

| 脚本 | 现象 | 现状 |
| --- | --- | --- |
| `ws_download.py` | 传 `id1,id2,id3` 直接打印「没有可下载的 id」，一个都不下 | 已改为 `re.split(r"[,\s]+")` 兼容逗号 / 空格 |
| `ws_rank.py --no-lua` | 只读紧跟 `--no-lua` 的**那一个**参数，空格分隔的其余 id 被静默丢弃（第 12 轮 8 个只标记进 1 个） | 已改为 `",".join(a[k+1:])` |

👉 通教训：**批量脚本的 id 参数一律先 `re.split(r"[,\s]+", " ".join(剩余参数))`**，别只取 `argv[k+1]`。
两个脚本都是「不报错、结果少一截」，靠 `tail` 才能发现。

### 16.3 `completeness.pending_ids` 是计数，不是清单

`ws_scan_progress.json` 里：

- 顶层 `pending_ids` —— **真正的 id 清单**（list）
- `completeness.pending_ids` —— **计数**（int，与顶层长度一致）

写账本时若对 `completeness.pending_ids` 做列表推导会直接 `TypeError: 'int' object is not iterable`。
正确做法：从顶层清单过滤，`completeness.pending_ids = len(...)`。

### 16.4 价值轨新 id 的 Lua 命中率会剧烈波动

| 轮次 | 新下载 id 数 | 含 Lua | 命中率 |
| --- | --- | --- | --- |
| 第 7 轮 | 9 | 3 | 33% |
| 第 11 轮 | 30 | 12 | 40% |
| 第 12 轮 | 8 | **0** | **0%** |

mostrecent 段的老作品 Lua 密度明显更低（纯建造 / 舰体占比高）。**每轮先拿 `--top` 与 `ids_downloaded`
求差集、优先吃库存**，把下载预算留给真正没货的时候。

## §17 第 16 轮：库存吃干期的工作方式 + 三处工程陷阱（2026-09-05）

**背景**：价值轨 `--top 24` 与 `ids_downloaded` 的差集已连续五轮趋近 0，
三个微批的「全新」段从 38 → 1 → 2 断崖式下降。**价值轨不再是主要供给，完整性轨与 `_r*c` 库存才是。**

1. 🔑 **FIX 清单里的「自匹配」意味着什么**：`diff_lua_batch.py` 输出
   `3793646592_vehicle_0.lua == 3793646592_vehicle_0.lua [未学习 3793646592]`——
   左右同名，表示该段此前**已被提取进主库**（只是没学）。这类自匹配成片出现时，
   用 `pick_lua_candidates.py --per-id N` 按 steam id 收敛（每 id 只留 1~2 段）比 `peek_lua.py` 装箱更省，
   因为 `peek` 会按分数把同一个作品的十几段都塞进来。
2. 🔧 **`_workshop_learned.json` 在 `AI相关\` 下，不在 `AI相关\_meta\`**。
   写账本时 `L = json.load(...)` 的路径写错会直接 FileNotFoundError。
   它是 **dict（id → 3 字段）**，`ids_learned = sorted(d.keys())`。
3. 🔴 **批次目录用「复制」而不是「移动」并入主语料**。
   例题末尾的「完整脚本：`../../../AI相关/_提取暂存/_bN/xxx.lua`」指向批次目录；
   按流程把 `_bN` 清空会让这些引用全部失效（历史上 `_r*c` 之所以保留就是为了避免这点）。
   正确做法：`shutil.copyfile` 复制进主库（供下轮差分），`_bN` 原样留作归档。
   `_mk_batch.py` 扫描时排除 `_b*`，不会造成重复统计。
4. 🔧 **改 README 索引表必须先 `find` 取真串再 `replace`**。本轮两次凭记忆拼锚点导致 `assert` 失败：
   ① `08` 行的「弹链 / 膛室两级…」在**第三列**（什么时候查）末尾，不在第二列；
   ② `05` 行的 `tilt` **不带反引号**。一律先打印目标行尾部 200~320 字符再拼锚点。
